# Deploying KARMA's free trust-oracle endpoint on Render (free tier)

This exposes `get_cross_chain_trust_score` (`src/plugins/trust_oracle.tool.ts`) over public HTTPS
on Render's free Web Service plan — the endpoint OKX.AI's A2MCP ASP listing needs
(`.claude/skills/okx-ai/references/identity-register.md` requires a real, publicly reachable
`https://` URL). It does **not** enable `karma.tool.ts` (skill economy), the on-chain indexer, or
Redis — the trust oracle reads chain state directly per call and needs none of that. For the full
production stack, see [docs/RUNTIME.md](../../docs/RUNTIME.md) instead.

No credit card, no server to patch, no manual TLS setup — Render terminates HTTPS for you on
`*.onrender.com` automatically.

## What you do by hand

1. **Sign up at [render.com](https://render.com)** (GitHub login is easiest — no card required for
   the free plan).
2. **New + → Blueprint**, connect this GitHub repo. Render reads `deploy/render/render.yaml`
   automatically and proposes one Web Service (`karma-trust-oracle`) on the **Free** plan, building
   from the existing `Containerfile`. Click **Apply**.
   - If you'd rather create it by hand instead of via Blueprint: New + → Web Service → connect the
     repo → Runtime: **Docker** → Dockerfile Path: `Containerfile` → plan **Free** → then copy the
     env vars from `render.yaml` into the dashboard's Environment tab yourself.
3. **Wait for the first build** (a few minutes — it runs `pnpm install && pnpm build` inside the
   Docker build per `Containerfile`).
4. **Verify:**
   ```bash
   curl https://karma-trust-oracle.onrender.com/health/liveness
   ```
   First hit after any idle period takes 30-60s (free tier cold start) — that's expected, not a
   failure.

That URL (`https://karma-trust-oracle.onrender.com`) is what goes into the OKX.AI ASP registration
endpoint field.

## If your first deploy hangs on "Waiting for internal health check"

Render's Docker-runtime health checker probes port `10000` by default — it does not read the
`PORT` env var to decide which port to probe, and `Containerfile` has no `EXPOSE` directive to tell
it otherwise. `render.yaml` already sets `HTTP_PORT=10000`/`PORT=10000` to match, so a fresh deploy
from this Blueprint shouldn't hit this. If you're seeing the app log
`Server listening on HTTP 0.0.0.0:3333` while the health check waits on port `10000` (i.e. you're
on an older copy of this Blueprint), fix it in the dashboard: service → **Environment** → set both
`HTTP_PORT` and `PORT` to `10000` → Save Changes triggers a redeploy.

## If the port is already right and it *still* times out on health check

Check the logs for `[KARMA] Skill event indexer started (backfill + live watch)`. Setting
`MCP_SAFE_MODE=false` + `PHAROS_CONTRACT_ADDRESS` (both required for the trust oracle tool itself)
also auto-starts KARMA's on-chain skill indexer (`src/index.ts`) — which `get_cross_chain_trust_score`
does **not** use, since it reads chain state live per call
(`src/plugins/trust_oracle.tool.ts`). Left at its default `KARMA_INDEXER_FROM_BLOCK=0`, the indexer
backfills from genesis — tens of millions of blocks on Pharos Atlantic, thousands of sequential RPC
calls — which can saturate a free-tier instance for the entire health-check window and starve
Render's port detection, even though the app itself is up and listening on the right port the whole
time. `render.yaml` pins `KARMA_INDEXER_FROM_BLOCK` near the current chain head to skip the
historical scan (exact value doesn't matter — it only needs to avoid the full-history scan; bump it
occasionally if it drifts far enough to matter again). Get the current value with:

```bash
curl -s -X POST https://atlantic.dplabs-internal.com \
  -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
# result is hex, e.g. "0x19a17e1" -> printf "%d\n" 0x19a17e1
```

then set `KARMA_INDEXER_FROM_BLOCK` to that decimal number in the dashboard's Environment tab.

## If you rename the service

`ALLOWED_HOSTS` / `ALLOWED_ORIGINS` in `render.yaml` are hardcoded to
`karma-trust-oracle.onrender.com` because KARMA's HTTP layer rejects any Host header not on that
allowlist (`src/index.ts` `isAllowedHost`). If you pick a different service name in the Render
dashboard, update those two env vars in the dashboard to match the actual `*.onrender.com` hostname
Render assigns, or the server will 403 every request with `Invalid Host`.

## Finding your API key

`MCP_API_KEY` is auto-generated by Render (`generateValue: true`) — find it under the service's
**Environment** tab after the first deploy. Whether callers need to send it is up to how you frame
the "free tool": share it in the ASP listing description for a light abuse-deterrent, or leave the
endpoint effectively open if OKX's A2MCP gateway is expected to front its own auth.

Example authenticated call once deployed:

```bash
curl -sS https://karma-trust-oracle.onrender.com/mcp \
  -H 'Content-Type: application/json' \
  -H "x-api-key: <MCP_API_KEY from the dashboard>" \
  -H 'Mcp-Method: tools/call' \
  -H 'Mcp-Name: get_cross_chain_trust_score' \
  --data '{
    "jsonrpc": "2.0",
    "id": "1",
    "method": "tools/call",
    "params": { "name": "get_cross_chain_trust_score", "arguments": { "evm_address": "0x0000000000000000000000000000000000000000" } }
  }'
```

## Known trade-off: cold starts

Render's free plan spins the service down after 15 minutes with no inbound traffic and takes
30-60s to wake back up on the next request. This is fine for `get_cross_chain_trust_score`, which
reads chain state fresh on every call and keeps no state between requests that would be lost on
sleep. It's not fine if you later add `karma.tool.ts` and rely on the on-chain indexer running
continuously in the background — that needs an always-on host instead (see the main README's
hosting discussion).

## Redeploying after changes

Render auto-redeploys on every push to the connected branch by default. To redeploy manually:
dashboard → service → **Manual Deploy → Deploy latest commit**.
