# KARMA ZK circuits

Circom + Groth16 circuits for the Stellar ZK hackathon track (synthesis §5,
plan T4–T5).

## Layout

```
circuits/
  src/agent_credential.circom        T4 — AgentCredentialProof (per-skill replay-guarded)
  src/reputation_aggregation.circom  T1.1 — ReputationAggregationProof (4-tuple aggregate)
  dummy/multiplier.circom            toolchain-validation circuit
  test/                              end-to-end snarkjs pipelines (compile → setup → prove → verify)
  scripts/install-toolchain.sh       downloads circom binary + installs snarkjs locally
  Makefile                           `make all` runs everything
```

The `bin/`, `build/`, `node_modules/`, and `ptau/*.ptau` directories are
gitignored — they are regenerated by `make all`.

## Quick start

```bash
cd circuits/
make toolchain     # downloads circom v2.2.3 + installs snarkjs locally (idempotent)
make dummy         # validates the toolchain end-to-end (multiplier circuit, ~5 s)
make credential    # T4 — AgentCredentialProof + happy + 5 negative tests (~2 min)
make rep-agg       # T1.1 — ReputationAggregationProof + happy + 6 negative tests (~16 min)
make all           # everything above
```

`make credential` is the deliverable for **T4** — its output is the `.zkey`,
`verification_key.json`, and witness/proof artefacts the Soroban verifier (T5)
consumes (`submit_credential` / `create_job`).

`make rep-agg` is the deliverable for **T1.1** — same outputs, consumed by the
Soroban verifier's `submit_aggregation_credential` entry point. The pot16
prepare-phase2 step dominates wall-time (~14 min); the actual prove/verify is
sub-second. Setup is one-shot — the resulting `.zkey` + verifying key are stable
inputs to every downstream consumer.

## Circuit — `AgentCredentialProof`

| Public input          | Meaning                                                                  |
|-----------------------|--------------------------------------------------------------------------|
| `skillId`             | the skill being invoked                                                  |
| `minReputation`       | the skill's on-chain reputation threshold                                |
| `nullifier`           | `Poseidon(credentialSecret, skillId)` — per-skill replay guard            |
| `credentialCommitment`| `Poseidon(credentialSecret)` — published when the credential is issued    |
| `jobHistoryRoot`      | issuer-published merkle root the commitment is a leaf under              |

| Private input         | Meaning                                                                  |
|-----------------------|--------------------------------------------------------------------------|
| `credentialSecret`    | agent's private credential secret (never revealed)                       |
| `reputationScore`     | actual score (only the `>= minReputation` fact is revealed by the proof) |
| `pathElements[8]`     | merkle siblings on the path from the leaf to the root                    |
| `pathIndices[8]`      | side at each level (0 = leaf-on-left, 1 = leaf-on-right)                 |

Tree depth = 8 (256 leaves) — adequate for the hackathon demo; production
scope would bump to 16 (`pot14`+) per the synthesis doc.

### Public-signal order (Soroban verifier contract MUST consume in this order)

```
[ skillId, minReputation, nullifier, credentialCommitment, jobHistoryRoot ]
```

This order is asserted by `test/agent_credential.test.mjs` so a future
reorder in the circuit fails the test before reaching the verifier.

## Trusted setup provenance

The Powers of Tau ceremony is **generated locally** by `make credential` —
a single-contributor phase-1 + phase-2 ceremony. This is acceptable for the
**testnet hackathon demo only**; a mainnet deployment would require a
multi-party Hermez ceremony tap (`pot14_final.ptau` etc.). The plan flags
this as deferred for the hackathon scope.

## Output → Soroban verifier

`make credential` writes `build/agent_credential/verification_key.json`
which is consumed by `contracts-soroban/agent_credential_verifier` (T5) as
the on-chain verifying-key bytes.

## Circuit — `ReputationAggregationProof` (T1.1)

A multi-tuple aggregate proof. An agent holds N reputation tuples — each tuple
is `(agentCommit, categoryId, score, jobCount)` published by the issuer (KARMA)
as a leaf in a periodic `epochRoot` Merkle tree. The circuit proves, without
revealing the tuples, scores, categories, or `credentialSecret`, that the agent
has N tuples all binding to the same secret, all members of `epochRoot`, with
categories strictly ascending (uniqueness), and weighted aggregate `Σ score ×
jobCount ≥ minTotal` plus `Σ jobCount ≥ minJobs`.

| Public input               | Meaning                                                              |
|----------------------------|----------------------------------------------------------------------|
| `minTotal`                 | weighted aggregate floor                                             |
| `minDistinctCategories`    | hardcoded N in v1 (= 4); kept public for v2 "K of M" forward-compat  |
| `minJobs`                  | engagement floor — total jobCount across all N categories            |
| `nullifier`                | `Poseidon(credentialSecret, epoch)` — per-epoch replay key            |
| `epochRoot`                | issuer-published Merkle root the leaves live under                    |

| Private input              | Meaning                                                              |
|----------------------------|----------------------------------------------------------------------|
| `credentialSecret`         | agent's private credential secret (never revealed)                   |
| `epoch`                    | scalar epoch id (binds nullifier to a specific snapshot)             |
| `categoryIds[N]`           | ascending category ids (u16 range; uniqueness via ordering)          |
| `scores[N]`                | per-category scores in [0, 100]                                      |
| `jobCounts[N]`             | per-category job counts in [1, 1023]                                 |
| `pathElements[N][depth]`   | Merkle siblings (one path per leaf)                                  |
| `pathIndices[N][depth]`    | side at each level                                                   |

**Sizing**: N=4 tuples × depth=8 (≤ 256 leaves per epoch). Compiled ≈ 9.7k
non-linear constraints, 20.8k wires → needs `pot16` (65536 powers). Future v2
with N=8 + depth=12 would need `pot18` and a multi-party ceremony.

**Public-signal order** (Soroban `submit_aggregation_credential` MUST consume in this order):

```
[ minTotal, minDistinctCategories, minJobs, nullifier, epochRoot ]
```

The TypeScript wrapper [`src/lib/zk/reputation_aggregation.ts`](../src/lib/zk/reputation_aggregation.ts)
locks the constants (`AGGREGATION_CIRCUIT_V1`) and exposes `parseAggregationPublicSignals`
so consumers reason about this in a typed view.
